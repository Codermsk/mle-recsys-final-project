# Рекомендации банковских продуктов

Рекомендательная система для банка: по профилю клиента и истории его продуктов модель
предсказывает, какие продукты клиент подключит в следующем месяце, и выдаёт топ-7.
Модель обучена на данных Santander Product Recommendation (17 месячных снимков базы
клиентов, январь 2015 - май 2016) и работает как веб-сервис с мониторингом.

**Стек:** Python 3.11, pandas, CatBoost, MLflow (SQLite + хранилище артефактов),
FastAPI, Docker Compose, Prometheus, Grafana.

## Бизнес-задача и её постановка

**Бизнес-задача.** Банк хочет предлагать клиенту продукты, которые ему действительно нужны:
вовремя предложить кредитную карту, зарплатный проект или депозит. Нерелевантные предложения
раздражают клиента и тратят ресурсы канала коммуникации, поэтому список должен быть коротким
и упорядоченным по вероятности отклика.

**Техническая задача.** Для каждого клиента на месяц t построить ранжированный список из 7
продуктов, которые он подключит в месяце t+1 (продукта не было в месяце t, он появился в t+1).
Продукты, которые у клиента уже есть, в список не попадают.

Задача решается как многоклассовая классификация: одна обучающая строка - пара
(клиент, подключённый продукт), признаки - профиль клиента и история его продуктов на месяц t.
Вероятности 24 классов сортируются, уже имеющиеся продукты исключаются, берутся первые 7.

**Метрики** (считаются по клиентам, у которых в целевом месяце появился хотя бы один продукт):

| Метрика | Что показывает |
|---|---|
| `MAP@7` | основная: насколько высоко в списке стоят подключённые продукты (метрика соревнования) |
| `precision@7` | доля угаданных продуктов в списке |
| `recall@7` | доля подключённых продуктов, попавших в список |
| `hit_rate@7` | доля клиентов, у которых угадан хотя бы один продукт |
| `coverage` | доля каталога, которая попадает в рекомендации |

Валидация по времени: обучение на признаках мая 2015 - февраля 2016, ранняя остановка на марте
2016, отложенный тест - признаки апреля 2016 и подключения мая 2016.

## Инфраструктура обучения

Эксперименты логируются в MLflow. Сервер хранит метаданные в SQLite (`mlflow/mlflow.db`),
а артефакты (модели, графики) - в отдельном хранилище, которое раздаёт сам сервер
(`--serve-artifacts`). По умолчанию это папка `mlflow/artifacts`, для S3 достаточно задать
переменные окружения (см. комментарий в скрипте).

```bash
bash scripts/run_mlflow.sh          # UI: http://localhost:5000
```

В эксперименте `bank_products_recsys` каждый запуск содержит параметры модели и набора признаков,
метрики на отложенном тесте, график важности признаков и саму модель. Финальная модель
зарегистрирована в Model Registry как `bank_products_recsys`.

Финальную модель можно переобучить без ноутбука - параметры берутся из `models/best_params.json`:

```bash
python -m src.train
```

Скрипт обучает модель на всех месяцах, сохраняет `models/model.bin` и `models/model_meta.json`
и выгружает признаки клиентов на последний месяц в `data/features_latest.parquet` - это
хранилище признаков для сервиса.

## Исследовательский анализ данных

Ноутбук `notebooks/01_eda.ipynb`. Основные выводы:

- 956 тыс. клиентов, 13.6 млн записей; в июле 2015 в базу пришло около 193 тыс. новых клиентов;
- почти все клиенты - резиденты Испании (99.6%), 71% пришли через каналы KHE, KAT и KFC;
- у 60% клиентов есть текущий счёт, у четверти нет ни одного продукта, почти у половины - ровно один;
- новые продукты в месяц подключают только 2.9-5.3% клиентов;
- пять продуктов дают 80% подключений: прямой дебет (27%), пенсия и зарплата (payroll, 15% и 13%),
  кредитная карта и текущий счёт (по 12%);
- зарплатные продукты (`nomina`, `nom_pens`, `cno`) сильно связаны между собой;
- есть сезонность: в июне 2015 всплеск налогов, пенсии и текущих счетов, в августе провал,
  в феврале 2016 - рост payroll.

## Признаки и обучение

Признаки строятся в `src/features.py` на месяц t:

- профиль: возраст, доход, стаж в банке, месяцев с первого контракта, пол, сегмент, канал
  привлечения, провинция, тип и статус клиента и др. (категориальные признаки CatBoost
  кодирует сам);
- месяц рекомендации (учитывает сезонность);
- владение каждым из 24 продуктов в текущем месяце и 4 предыдущих (лаги 1-5);
- число продуктов, число подключений и отключений за окно, число изменений по каждому продукту.

Результаты на отложенном тесте (27.9 тыс. клиентов с новыми продуктами в мае 2016):

| Модель | Признаков | MAP@7 | precision@7 | recall@7 | hit_rate@7 | coverage |
|---|---|---|---|---|---|---|
| Популярность за 4 месяца (бейзлайн) | - | 0.6372 | 0.1773 | 0.9597 | 0.9631 | 0.833 |
| CatBoost, профиль + текущие продукты (`base`) | 45 | 0.8133 | 0.1810 | 0.9848 | 0.9872 | 0.917 |
| **CatBoost, + история за 5 месяцев (`full`)** | 167 | **0.8660** | 0.1812 | 0.9856 | 0.9876 | 0.917 |
| CatBoost `full`, depth 8, l2 10 | 167 | 0.8651 | 0.1812 | 0.9860 | 0.9880 | 0.917 |

Если усреднять MAP@7 по всей базе (как на Kaggle, у 97% клиентов новых продуктов нет), бейзлайн
даёт 0.0191, лучшая модель - 0.0260.

Выводы:

- `precision@7` у всех моделей около 0.18: клиент обычно подключает 1-2 продукта, поэтому
  потолок метрики низкий. Модели различаются тем, на какое место ставят нужный продукт, - это
  видно по `MAP@7`;
- CatBoost на профиле и текущих продуктах поднимает MAP@7 с 0.637 до 0.813, история продуктов
  за 5 месяцев - ещё до 0.866. Payroll-продукты часто отключаются и снова подключаются, и
  счётчики изменений это ловят;
- более глубокая модель качество не улучшила, выбрана `full` с depth 6 (обучение в 1.3 раза быстрее);
- самые важные признаки: наличие текущего счёта и прямого дебета, месяц рекомендации, число
  изменений по пенсии и прямому дебету, возраст, стаж в банке;
- лучше всего модель угадывает первым текущий счёт (96% случаев), прямой дебет (89%) и кредитную
  карту (68%). Хуже всего - зарплату: она почти всегда в топ-7, но первой стоит только в 7% случаев,
  потому что подключается вместе с пенсией и модель не может их различить.

Финальная модель обучена с лучшими параметрами на всех месяцах (441 тыс. строк, 690 итераций -
лучшая итерация на валидации с запасом 15%) и зарегистрирована в MLflow Model Registry.

## Инфраструктура применения

Сервис (`service/app.py`) при старте загружает модель и хранилище признаков. Для клиента из
хранилища рекомендации строит модель, для нового клиента без истории - список самых популярных
продуктов за последние месяцы.

Запуск сервиса вместе с мониторингом:

```bash
python -m src.train              # если модели и признаков ещё нет
docker compose up --build -d
```

| Сервис | Адрес |
|---|---|
| API рекомендаций | http://localhost:8000 (документация: /docs) |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 (admin / admin, дашборд «Bank recsys») |

Если порт 3000 занят, Grafana можно поднять на другом: `GRAFANA_PORT=3001 docker compose up -d`.

Нагрузка для проверки мониторинга:

```bash
python scripts/simulate_traffic.py --duration 300 --rps 5
```

Описание метрик и дашборда - в [monitoring.md](monitoring.md).

## API

`GET /health` - статус и версия модели.

`GET /recommendations/{client_id}?k=7` - рекомендации для одного клиента.

```bash
curl "http://localhost:8000/recommendations/1375586?k=3"
```

```json
{
  "client_id": 1375586,
  "recommendations": [
    {"product": "ind_nom_pens_ult1", "name": "Пенсия (payroll)", "score": 0.26849},
    {"product": "ind_nomina_ult1", "name": "Зарплата (payroll)", "score": 0.26006},
    {"product": "ind_cno_fin_ult1", "name": "Зарплатный счёт", "score": 0.20994}
  ]
}
```

Если клиента нет в хранилище признаков, сервис отвечает списком популярных продуктов (score -
доля продукта среди подключений за последние месяцы), а в Prometheus такой ответ считается
с меткой `source="popular"`.

`POST /recommendations` - рекомендации для списка клиентов (до 1000 за запрос).

```bash
curl -X POST http://localhost:8000/recommendations \
     -H "Content-Type: application/json" \
     -d '{"client_ids": [1375586, 1050611], "k": 3}'
```

`GET /metrics` - метрики для Prometheus.
